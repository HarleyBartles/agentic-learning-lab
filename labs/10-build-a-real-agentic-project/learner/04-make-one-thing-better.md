# 4 — Make one thing meaningfully better

Take the weakness you identified and run one deliberate improvement cycle.

Start from the problem you actually observed.

For example:

- visual hierarchy is weak;
- spacing feels cramped;
- the tone is wrong;
- the structure is confusing;
- the copy is generic;
- an interaction is awkward;
- the page behaves badly at a narrow width.

Ask the worker to improve that weakness while keeping the rest of the project intent stable.

If the problem is clearly a domain-quality problem, consider giving the worker better domain guidance before it tries again.

For a website, that might be suitable design guidance or a design skill.

If you do that, keep the comparison as controlled as practical:

```text
same project
same intent
same model where practical
+
better domain provision
```

Then compare the before and after result.

Do not settle for `the second one is better`.

Name what actually changed and whether it solved the weakness you chose.

If extra domain provision was the important change, notice the distinction:

> **We did not simply ask harder. We changed what expertise the worker had available.**

You do not need to compare different models in this lab.

When the project is in a state you might be willing to accept, move to the final card.
